# Legal input audit: empty text and effective rights

This is a **focused, reproducible audit**, not a claim that all three formats
are fully conformant. It checks whether existing mapping rules wrongly reject
or lose content in valid common documents. The complete list of documented
support and remaining gaps is in [STANDARD_SCOPE.md](STANDARD_SCOPE.md).

| Clause / case | Before this change | Public result now | Evidence |
| --- | --- | --- | --- |
| Atom text constructs may contain empty or whitespace-only text; an empty title is discouraged, not forbidden ([RFC 4287 §4.1.1.1](https://www.rfc-editor.org/rfc/rfc4287#section-4.1.1.1), [§3.1](https://www.rfc-editor.org/rfc/rfc4287#section-3.1)) | Empty feed/entry titles became `None` and a false missing-title diagnostic; empty summary/rights/source text disappeared. | Text/HTML/XHTML title, subtitle, summary, rights and source text preserve `Some("")` or original spaces. A truly missing title remains `None` with a diagnostic; malformed XHTML without its required div remains invalid. | `atom_legal_text_test.mbt`, `samples/atom1_legal_empty_and_rights.xml` |
| Atom XHTML's outer div is excluded from content ([RFC 4287 §3.1.1.3](https://www.rfc-editor.org/rfc/rfc4287#section-3.1.1.3), [§4.1.3.3](https://www.rfc-editor.org/rfc/rfc4287#section-4.1.3.3)) | Fragment omitted the outer div, including its class/title and xml:lang/xml:base attributes; only effective language and raw base declarations survived. | Fragment still omits the wrapper in `markup`, but adds `container_attributes` with expanded XML names, decoded values, and source order. Existing language/base fields stay available. Caller chooses presentation/sanitization. | `xhtml_test.mbt`, `samples/atom1_xhtml_container.xml`, `tools/check_xhtml_container_reference.py` |
| Atom external/Binary content requires a summary element, but its text is not required to be non-empty ([RFC 4287 §4.1.2](https://www.rfc-editor.org/rfc/rfc4287#section-4.1.2)) | Present empty summary was treated as missing and produced a false diagnostic. | `Some("")` marks the present summary; both external and Base64 content remain structured in `atom_body`. | Same Atom regression; CLI JSON and feedparser intersection |
| Entry without its own rights uses the containing feed's rights ([RFC 4287 §4.2.10](https://www.rfc-editor.org/rfc/rfc4287#section-4.2.10)) | Entry `rights` was absent even when a preceding feed rights element applied. | Effective entry `rights`, `rights_kind`, and optional XHTML fragment inherit feed values. Own rights, including `Some("")`, take precedence. Stand-alone Entry has no invented feed context; source rights remain source metadata. | Same Atom regression and CLI JSON; independent XML direct-child check |
| JSON Feed nonblank string `id` is opaque; readers must discard items with blank IDs, while `tags` have any plain-text values ([JSON Feed 1.1 items and reader suggestions](https://www.jsonfeed.org/version/1.1/)) | An earlier correction retained blank IDs based on the item declaration while overlooking the reader guidance; empty tag values were skipped. | Nonblank string IDs survive byte-for-byte, including surrounding whitespace; empty/whitespace-only IDs diagnose and discard the item. Empty text/HTML content and string tags, including empty strings, remain valid. | `json_feed_test.mbt`, `samples/jsonfeed11_opaque_strings.json`, `tools/check_legal_input_reference.py` |
| JSON Feed attachment `mime_type` is required in a published feed, but readers can recover if it is missing ([JSON Feed 1.1 attachments and reader suggestions](https://www.jsonfeed.org/version/1.1/)) | An attachment with a usable URL was discarded if `mime_type` was missing. | Retain the URL and remaining metadata in source order, expose `media_type = None`, and diagnose the declaration; an absent/blank URL still drops that attachment. This is reader recovery, not a claim that the feed is valid. | `attachments_test.mbt`, `samples/jsonfeed11_attachment_recovery.json`, `tools/check_json_attachment_recovery.py` |
| Atom Date construct requires uppercase `T` and `Z`; generic RFC 3339 permits lowercase ([RFC 4287 §3.3](https://www.rfc-editor.org/rfc/rfc4287#section-3.3), [RFC 3339 §5.6](https://www.rfc-editor.org/rfc/rfc3339#section-5.6)) | `normalize_date` treated Atom and JSON Feed the same and accepted lowercase in Atom. | `normalize_date` rejects lowercase `t`/`z` for Atom while accepting both for JSON Feed; stored date strings remain unmodified. | `date_author_boundary_test.mbt`, `samples/atom1_date_case.xml`, `samples/jsonfeed11_empty_author_date.json` |
| RFC 3339 `-00:00` and mail-date `-0000` denote a known UTC time with unknown original local offset ([RFC 3339 §4.3](https://www.rfc-editor.org/rfc/rfc3339#section-4.3), [RFC 2822 §3.3](https://www.rfc-editor.org/rfc/rfc2822#section-3.3)) | `normalize_date` rejected these legal dates as `UnsupportedTimeZone`, even though the UTC instant is known. | `NormalizedDate.offset_known = false`; UTC and Unix seconds remain available, raw date remains unchanged. `offset_minutes = 0` is an arithmetic value and does not claim the original local zone was UTC. Z, +00:00, and +0000 set `offset_known = true`. | `date_unknown_offset_test.mbt`, three `samples/*unknown_offset*` mirrors, `tools/check_unknown_offset_reference.py` |
| Announced positive leap seconds allow `:60` in RFC 3339 and RSS mail dates ([RFC 3339 §5.7](https://www.rfc-editor.org/rfc/rfc3339#section-5.7), [NIST table](https://www.nist.gov/pml/time-and-frequency-division/time-realization/leap-seconds)) | `normalize_date` rejected every `:60` as invalid calendar date, including valid Atom/JSON/RSS dates. | Validate after applying the declared offset against a dated snapshot of all 27 announced UTC dates. Preserve `23:59:60` in UTC output, mark `is_leap_second`, use the preceding POSIX second for `unix_seconds`; reject unannounced dates. | `date_leap_second_test.mbt`, `samples/LEAP_SECONDS_NIST_2026-10-23.md`, three `samples/*leap_second*` mirrors, `tools/check_leap_second_reference.py` |
| Atom `href=""` and external `src=""` are present, empty IRI references ([RFC 4287 §4.2.7.1](https://www.rfc-editor.org/rfc/rfc4287#section-4.2.7.1), [§4.1.3.2](https://www.rfc-editor.org/rfc/rfc4287#section-4.1.3.2), [RFC 3987 §2.2](https://www.rfc-editor.org/rfc/rfc3987#section-2.2)) | Empty links and enclosures disappeared, external content was diagnosed as invalid, and an entry with an empty alternate URL could get a false missing-link diagnostic. | Feed/entry/source links, Atom enclosure and external body preserve `""` under raw parsing; source-aware APIs resolve them against each element's effective `xml:base`. Missing attributes still diagnose. RSS required enclosure URLs retain their own nonblank rule. | `atom_empty_iri_test.mbt`, `samples/atom1_empty_iri_references.xml`, `tools/check_atom_empty_iri_reference.py` |
| Atom Person `name` and category `term` require presence, while link/category display strings may be empty ([RFC 4287 §3.2.1](https://www.rfc-editor.org/rfc/rfc4287#section-3.2.1), [§4.2.2](https://www.rfc-editor.org/rfc/rfc4287#section-4.2.2), [§4.2.7.5](https://www.rfc-editor.org/rfc/rfc4287#section-4.2.7.5)) | An explicit empty or whitespace-only name became an invalid author and could trigger false author inheritance; an empty/whitespace category term disappeared; empty/whitespace labels and link/enclosure titles were lost. | Retain declared raw name, term, label and title strings, including `""`; distinguish absent required name/term with diagnostics. Preserve declared empty category scheme as a raw IRI reference. | `atom_declared_metadata_test.mbt`, `samples/atom1_declared_empty_metadata.xml`, `tools/check_atom_declared_metadata_reference.py` |
| JSON Feed author `name` is an optional plain-text string ([JSON Feed 1.1 authors](https://www.jsonfeed.org/version/1.1/#the-structure-of-a-feed)) | Explicit empty/whitespace name became absent; an author with only that field was dropped. | Preserve exact declared `name` and inheritance in both versions, including empty/whitespace. A truly empty author object is still invalid. | Same JSON sample, `json_feed_test.mbt` |
| Explicit HTTP(S) source URL must have a usable authority ([RFC 3986 §3.2](https://www.rfc-editor.org/rfc/rfc3986#section-3.2)); Atom uses IRI references and `xml:base` | A nonempty authority such as `:80` or `example.test:bad` passed entry validation, then relative fields generated scattered resolution diagnostics. | Both source-aware APIs reject those malformed sources first. Common invalid ASCII host characters are rejected; Unicode IRI hosts and nested relative `xml:base` stay usable. | `uri_source_boundary_test.mbt`, `uri_wbtest.mbt`, `samples/atom1_iri_host.xml`, `tools/check_source_authority_reference.py` |
| Bracketed HTTP(S) source host must be an IPv6 address or RFC 3986 IPvFuture literal ([RFC 3986 §3.2.2](https://www.rfc-editor.org/rfc/rfc3986#section-3.2.2)) | Any nonempty bracket content, including `[text]` and malformed IPv6, passed source validation. | Eight-group/compressed/IPv4-tail IPv6 shapes and IPvFuture syntax pass; malformed forms fail before resolution across feed and standalone entry inputs. Raw `parse` remains unchanged. | `uri_wbtest.mbt`, `uri_source_boundary_test.mbt`, `samples/atom1_ip_literals.xml`, `tools/check_source_authority_reference.py` |
| RSS item may contain only a title or only a description ([RSS 2.0 item](https://www.rssboard.org/rss-specification#hrelementsOfLtitemgt)) | Already supported. | Existing behavior retained; no identifier is invented for an item without guid/link. | `rss_item_required_test.mbt`, `samples/rss2_anonymous_items.xml` |
| Real RSS item creators often use the Dublin Core `creator` property for a name, distinct from RSS item `author` email ([DCMI Metadata Terms](https://www.dublincore.org/specifications/dublin-core/dcmi-terms/#creator), [RSS 2.0 item author](https://www.rssboard.org/rss-specification#hrelementsOfLtitemgt)) | Hacker News `dc:creator` names were lost while entries otherwise parsed successfully. | Direct, exact-namespace Dublin Core creator maps to `AuthorSource::DublinCore` name; RSS core author remains raw email. Order, aliases, scope and invalid markup have regressions. | `real_hn_rss.xml`, `rss_dublin_creator_test.mbt`, `tools/check_diverse_real_reference.py` |
| Atom link `hreflang` is an RFC 3066 language tag; tags are case-insensitive ([RFC 4287 §4.2.7.4](https://www.rfc-editor.org/rfc/rfc4287#section-4.2.7.4), [RFC 3066 §2.1](https://www.rfc-editor.org/rfc/rfc3066#section-2.1)) | Invalid language declarations were silently accepted and differently capitalized alternate tags evaded duplicate diagnostics; explicitly empty values were collapsed into absence. | Preserve original `hreflang` including `""`, validate RFC 3066 syntax without consulting the language registry, and diagnose repeated alternate tags regardless of case. | `atom_link_language_test.mbt`, `samples/atom1_link_languages.xml`, `tools/check_atom_link_language_reference.py` |
| RSS dates use RFC 822 case-insensitive named tokens and allow UTC zone `Z` ([RFC 822 §3.4.7](https://www.rfc-editor.org/rfc/rfc822#section-3.4.7), [§5.1](https://www.rfc-editor.org/rfc/rfc822#section-5.1)) | Mixed-case weekday/month/zone and `Z` were falsely marked unnormalized. | Normalize valid forms while retaining the raw date; non-Z military zones remain raw with `UnnormalizedRssDate` because RFC 1123 identifies their sign ambiguity. | `rss_date_case_test.mbt`, `samples/rss2_case_and_zone.xml`, `tools/check_rss_case_zone_reference.py` |

`tools/check_legal_input_reference.py` checks both byte-mirrored samples.
Python feedparser 6.0.11 independently parses the Atom fixture and agrees on
entry IDs, empty display titles/summary, explicit empty rights, and source
metadata. It strips the feed title's spaces and serializes sanitized XHTML;
FeedLens retains the original spaces and an unsanitized namespaced fragment.
feedparser does not project inherited feed rights on this fixture, so Python
ElementTree checks which entries directly declare rights and the library test
asserts RFC 4287's inheritance. Python's standard JSON parser independently
checks the JSON fixture's exact IDs, content, and tags against Native CLI JSON.
This comparison does not use live network feeds or claim broad conformance.

## Still requiring audit before the application

- Atom content's common MIME parameters now have legal and invalid regression
  cases plus an independent email/feedparser intersection. MIME comments and
  extension parameter syntax, full Atom IRI, future leap-second announcements, permitted extension
  points, and remaining cardinality rules still need a larger corpus.
- RSS source-defined optional metadata is mapped; extension modules and HTML
  presentation remain outside the core reader model.
- JSON Feed extension objects may be ignored by readers, but the remaining
  author/attachment/date edge cases need a documented compatibility corpus.
- The WP Tavern projections compare matching stories across all three formats.
  Three additional publisher snapshots cover RSS channel metadata, Atom HTML
  and missing-author diagnostics, and JSON HTML with author inheritance.
  They do not prove every optional field or fully valid Atom behavior across
  a broad set of publishers; xkcd's archived Atom input lacks required authors.
